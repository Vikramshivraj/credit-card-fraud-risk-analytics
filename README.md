# Credit Card Fraud Risk Analytics

An end-to-end data analytics and machine-learning project that explores credit-card transactions, identifies fraud patterns, scores transaction risk, and presents investigation insights through SQL, Python, and Power BI.

**Author:** Vikram Singh  
**Tools:** Python · pandas · NumPy · scikit-learn · SQLite · SQL · Power BI · Matplotlib · Seaborn

> **Dataset:** [Kaggle Credit Card Fraud Detection](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud). The dataset contains anonymised transactions made by European cardholders in September 2013. The source data has 284,807 rows and 492 fraud cases.

## Project workflow

1. **Data quality:** load the raw CSV, inspect missing values and duplicates, and remove exact duplicate records.
2. **Exploratory analysis:** compare fraud and legitimate transactions, study transaction amounts, and analyse relative time patterns.
3. **SQL analysis:** answer business questions with SQLite queries, including aggregations, `CASE`, CTEs, subqueries, and window functions.
4. **Model training:** train a Logistic Regression pipeline with class weighting and feature scaling. Split the data before fitting preprocessing steps to reduce leakage.
5. **Risk scoring:** convert model probabilities into a 0–100 score and Low, Medium, and High risk tiers.
6. **Threshold selection:** choose an operating threshold using a cost assumption on training data, then evaluate on held-out test data.
7. **Reporting:** export scored test transactions and summary metrics, create static Python charts, and explore results in Power BI.

## Key results

The figures below are from the current notebook run and its held-out test set. They are experimental results, not evidence of a deployed or production fraud system.

| Metric | Result |
|---|---:|
| Raw transactions | 284,807 |
| Exact duplicate rows removed | 1,081 |
| Transactions after de-duplication | 283,726 |
| Fraud rate after de-duplication | ~0.17% |
| ROC-AUC | 0.965 |
| PR-AUC | 0.668 |
| Recall at default 0.5 threshold | 87.4% |
| Precision at default 0.5 threshold | 5.6% |
| High-risk alerts in test set | 115 |
| Fraud cases caught in High tier | 75 of 95 |
| High-tier precision | 65.2% |

### What these results mean

- Fraud is rare, so accuracy alone can be misleading. Predicting every transaction as legitimate would be about 99.8% accurate while detecting no fraud.
- At the default 0.5 threshold, recall is high but precision is low, creating many false-positive alerts.
- The selected High-risk tier is a much smaller review queue: 115 alerts, of which 75 were fraud in this test split.
- Transaction amount alone is not sufficient to identify fraud; average and median amounts tell different stories.

## Run the project locally

### 1. Get the dataset

Download `creditcard.csv` from the [Kaggle dataset page](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud) and place it at:

```text
data/creditcard.csv
```

### 2. Set up Python

Open the repository folder in VS Code. Install the Python and Jupyter extensions, then run these commands in the terminal.

**Windows PowerShell**
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

If PowerShell blocks activation, use Command Prompt and run `.venv\Scripts\activate.bat`, or install dependencies with the environment's Python executable directly.

**macOS/Linux**
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 3. Run the notebook

Open `notebooks/fraud_risk_analytics.ipynb`, select the `.venv` Python kernel, and run the cells from top to bottom. The notebook creates `data/fraud.db`, `data/risk_scored_transactions.csv`, `data/results.json`, and the PNG dashboard images.

### 4. Explore the SQL

Open `sql/fraud_analysis.sql` and run the queries against the generated `data/fraud.db` using a SQLite extension in VS Code or another SQLite client. The notebook creates the `transactions` and `scored_transactions` tables.

### 5. Open Power BI

Open `dashboards/fraud_risk.pbix` in Power BI Desktop. The accompanying [Power BI guide](POWERBI_GUIDE.md) documents the recommended measures and visuals.

## Model and evaluation notes

- **Model:** Logistic Regression with `class_weight="balanced"` and feature scaling inside a scikit-learn pipeline.
- **Features:** anonymised `V1`–`V28` columns, transaction `Amount`, and a derived relative-time feature.
- **Risk score:** predicted probability multiplied by 100; tiers are defined in the notebook.
- **Evaluation:** ROC-AUC, PR-AUC, precision, recall, and alert counts are more informative than accuracy for this imbalanced classification task.

## Limitations and responsible interpretation

- The `V1`–`V28` fields are anonymised PCA features; merchant, location, customer history, and payment-channel context are unavailable.
- The data is from September 2013 and covers a short period; patterns may not generalise to current transactions.
- The review cost used for threshold selection is an illustrative assumption, not a verified bank operating cost.
- Class weighting can make predicted probabilities poorly calibrated. Treat the score as a risk-ranking signal, not a reliable real-world probability without further calibration.
- Results depend on the train/test split and the relatively small number of fraud cases in the test set.
- This is a learning and portfolio project, not a live payment-processing or production fraud-detection service.

## Possible next improvements

- Calibrate predicted probabilities and evaluate thresholds with realistic review-cost assumptions.
- Compare Logistic Regression with tree-based models such as XGBoost or LightGBM.
- Add explainability with SHAP, drift monitoring, and more representative time-based validation.
- Improve Power BI formatting and add clear definitions for each KPI.

## Interview revision

- **Why not accuracy?** Fraud is only about 0.17% of the cleaned data, so a model can be highly accurate while missing every fraud case.
- **Precision vs recall?** Precision measures how many flagged transactions are actually fraud; recall measures how many actual fraud cases are caught.
- **Why PR-AUC?** Precision-recall metrics focus on the rare positive class and help assess performance under severe class imbalance.
- **Why remove duplicates?** Duplicates can distort analysis and may cause overly optimistic evaluation if related copies appear across train and test sets.
- **Why use a pipeline?** It keeps preprocessing and model training together and helps avoid fitting the scaler on the test set.
- **Why use risk tiers?** Tiers turn raw model scores into a prioritised review queue with a more manageable number of high-priority alerts.
